# Writing workflow

This guide is the shortest path from a new article to a release-ready static build.

## 1. Create a post

For the guided workflow, run:

```bash
npm run new-post
```

The prompt asks for the article title, slug, description, category, tags, optional author, language, draft/featured state and Markdown or MDX format. The suggested slug is derived from the title and normalized before the file is created.

New posts are drafts by default. The command refuses to overwrite an existing slug, including when the existing post uses the other supported extension.

For a fast non-interactive draft, keep using:

```bash
npm run new-post -- my-post
```

That creates `src/content/posts/my-post.md` with safe starter values. To create MDX instead:

```bash
npm run new-post -- my-post.mdx
```

or:

```bash
npm run new-post -- my-post --mdx
```

## 2. Edit frontmatter

The generator writes a stable frontmatter shape and leaves optional fields out when they are not needed.

```yaml
---
title: "A useful, specific title"
description: "A standalone summary for readers and search results."
summary: "A concise direct answer shown near the top of the article."
date: 2026-08-31
category: "Engineering"
tags: ["Astro", "Static Sites"]
draft: true
noindex: false
featured: false
lang: "en"
---
```

Common optional fields are:

```yaml
summary: "A concise direct answer shown near the top of the article."
lastModified: 2026-09-03
author: "Your Name"
cover:
  src: "/images/posts/my-post/cover.webp"
  alt: "Diagram showing the publishing workflow"
```

Use `YYYY-MM-DD` for `date` and `lastModified`. `summary` is optional plain text for the visible Quick Answer block and should not simply duplicate `description`. See [Content authoring](content.md) for the complete field semantics.

There is no Related Posts frontmatter field. Keep `category` and `tags` truthful and consistent: article recommendations are generated automatically at build time from exact shared labels, without manual related-post IDs.

Previous / Next navigation also needs no authoring field. Published discoverable posts with the same exact `category` are connected automatically by publication date.

## 3. Write Markdown or MDX

Use `.md` for normal Markdown. Nothing about the MDX component layer is required for Markdown posts.

Use `.mdx` only when the article needs a component such as Callout, Accordion or YouTube. See [MDX components](mdx-components.md) for copyable imports and examples.

The page layout already renders the article title as H1, so begin body sections at H2 (`##`).

For body images, prefer portable Markdown destinations: public-root paths such as `/images/...`, stable HTTP(S) URLs, or valid content-relative paths such as `./image.webp` and `../images/image.webp`. Do not paste local application/file URIs into content. See [Content authoring](content.md#body-images).

## 4. Preview while writing

Start Astro's development server:

```bash
npm run dev
```

Published posts work normally. Draft posts are also available during development at their direct article URL, for example:

```text
/posts/my-post/
```

Drafts remain excluded from normal published-content lists and are still excluded from production builds. This makes it possible to keep `draft: true` while writing and reviewing locally.

Pagefind's complete static index is not generated by `npm run dev`. Search should be verified after a full build.

## 5. Check the content

Run the author-facing content check while writing when useful:

```bash
npm run check:content
```

Blocking problems are reported as `ERROR`; editorial suggestions are reported as `WARN`. Each diagnostic includes the source file and, when practical, a concrete fix. Warnings do not block a release. Non-portable Markdown image sources are blocking because they cannot be relied on after deployment.

Before publishing, run the complete release gate:

```bash
npm run check
```

This covers type checking, linting, formatting, unit tests, configuration/content checks, the static build, Pagefind, generated links, sitemap, safety checks and the template regression smoke test.

## 6. Review drafts and publish

List all current draft posts with:

```bash
npm run drafts
```

When an article is ready, change:

```yaml
draft: true
```

to:

```yaml
draft: false
```

There is deliberately no automatic Git commit, push or deployment step. Publishing state remains an explicit frontmatter edit that is easy to review in a diff.

Run `npm run drafts` again if you want to confirm which posts still remain unpublished.

## 7. Preview the final static output

Build the same static site shape used for deployment, including the Pagefind index:

```bash
npm run build
npm run preview
```

Use this path for final browser review. `npm run dev` is optimized for the writing loop; `npm run build && npm run preview` is the final static-output preview.

## 8. Run the production smoke build and deploy

Supply the real production HTTPS origin:

```bash
SITE_URL=https://your-domain.example npm run build:production
```

The production command rejects a missing or placeholder site origin, then builds the static output and Pagefind index.

After the smoke build passes, deploy `dist/` with your normal hosting workflow. AstroPublishKit does not commit, push or deploy content automatically.
